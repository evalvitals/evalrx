# Adaptive benchmark diagnosis

Use the same datasets, scorers, and final repair validation with an agent that chooses the next diagnostic action:

```bash
python -m evalrx.benchmark.run --modality llm --model gemini-3.6-flash \
  --dataset bbh_causal_judgement
```

The existing judge/coder options apply. Replace modality and dataset for image/audio tasks. Gemini probability support is probed on the actual model; unsupported logprobs and raw logits are never simulated.

Agentic diagnosis is the default. No mode or per-stage enable flags are needed. `--max-actions` optionally changes the default budget of 12 controller decisions. The hidden legacy `--diagnosis-mode fixed` option remains available only to replay historical fixed-pipeline comparisons; current default runs are a different protocol from those historical results.

## Controller scope

The controller can choose catalog probes, request custom probes, run statistics, explore data, cluster failures, propose hypotheses, and test them on EXPLORE. It can gather more evidence after an empty diagnosis, subject to action and tool-call caps. Custom M1 probes and M2 tool generation default on in agentic mode across modalities; The existing `--no-allow-codegen` disables custom M1/repair generation, and `--no-m2-codegen` disables M2 generation.

Repair and surgery are excluded from the benchmark controller's tool registry. After the investigation, the host runs repair search on EXPLORE and validates a frozen winner once on CONFIRM. The controller cannot inspect confirmation feedback and adapt to it. `--held-out` currently requires fixed mode; agentic mode rejects that combination before loading a model.

Agentic repair does not inject built-in floor candidates. The agent can still propose known repair methods. The existing repair tier/capability constraints and maximum repair rounds remain enforced. This mode is bounded adaptive diagnosis, not an unlimited autonomous training loop.

## Triage policy (opt-in)

`--m1-policy triage_active` replaces the diagnosis with a host-side triage controller (`evalrx/eval_agent/probing/`, design in `evalsmith/probing/probing_design_mix.md`). The default `--m1-policy judge` is unchanged.

```bash
python -m evalrx.benchmark.run --modality vlm --model qwen3.5-0.8b-vl --backend hf_local \
  --dataset pope_adversarial --limit 200 --attn-impl eager \
  --m1-policy triage_active --run-tag triage0
```

After Stage 0 and the same EXPLORE/CONFIRM split as the loop, it draws `--triage-n-fail` FAIL cases (default 8) and gold-matched PASS controls from EXPLORE with a nested sampler, then runs a fixed battery exactly as written — `answer_extraction_audit`, `termination_audit` (no continuation), `modality_ablation(mode="swap")`, `attention_knockout(target="prediction")`, `self_consistency` (5 samples per case), `prompt_contrast` with two neutral wrappers around the verbatim question, `prompt_contrast` with an instruction not to default to a negative answer (yes/no tasks only), `embed_lens(layer=0.9)` and `patchscope(target="prediction", media_layers=3)` — with no backfill, case cap or generated probes. After the battery, fixed rules choose what runs next (see below). No judge is called (unless `--triage-explanations judge`, below), M2–M5 do not run, and CONFIRM never reaches the controller. Outputs go to `<run>/probing/`: `selection_trace.jsonl` (every action and every decision with its rule, condition and the candidates it passed over), `cost_ledger.jsonl` (each Stage 0 invocation separate from the actions' new calls), `observations/<action_id>.json` with an `index.jsonl`, `split_manifest.json` (every sample revision), and `triage_report.{json,md}` with H/N/U/S/X route labels traced to case, field, action and fidelity verdict. Outcomes are typed (`ok`, `unsupported`, `failed`, `unfaithful`) and never written as zeros. Rerunning the same command reads finished actions back by content identity instead of re-running them; `--triage-budget-sec` skips an action once the budget is spent or once the estimate of its next chunk exceeds what is left: the step's own measured seconds per case in this run, else the most expensive case measured so far (no per-analyzer cost prior: costs measured across input sizes do not keep their ratios, see below). The budget is charged with the evidence the run reads, each observation at the cost of its first execution, plus its judge calls, so a resumed run, or a second scheduler on the same ledger, is charged what its evidence cost rather than what this invocation happened to execute.

**Expansion.** At the start of each round the sample doubles along the sampler's rank prefixes, up to `--triage-max-fail` FAIL cases (default 32; at or below `--triage-n-fail` disables it), while a gap holds that more cases can close: a route whose FAIL-minus-PASS difference is positive while its 95% interval (Newcombe) still includes zero, or a gold stratum whose S cohort or stable PASS controls has fewer than 8 cases. The battery then runs again only where it must. Every step's per-case rows are independent of the batch, so steps run on the new cases alone and keep the old rows: `embed_lens` and `patchscope` tell question words (and `embed_lens` recurring media words, from the first 16 distinct images) from a fixed reference — EXPLORE in the sampler's rank order — instead of the batch, `tuned_lens` is fit once on the first 32 of those cases (cached on the model), and `causal_trace` seeds its noise from each case's content instead of its position; `self_consistency` draws each case's samples under a seed of its content too, so the U sampling check is the same in every run. No route reads `embed_lens` or `patchscope`, so they still wait until the sample stops growing. Each step's observations are chunks over disjoint case sets, indexed by the step's identity without its cases, so a later invocation with a larger cap also reads earlier chunks back and runs only uncovered cases. An edit whose self-check refuses on any chunk is refused on every case. Steps run in chunks of `--triage-chunk` cases (default 8, FAIL and PASS alternating), with the budget checked before each chunk, so an action whose cost nobody knew overshoots by at most one chunk; a chunk that raises stops the rest of the step. Drawing 8 FAIL cases at once and expanding from 4 give every case the same record for the same calls (`tests/test_eval_agent/test_probing_mvp2.py`).

**Rule-chosen follow-ups.** Each route has ordered layers (`evalrx/eval_agent/probing/rules.py`), each a question with a default representative and fallbacks: H1 stricter re-ask, H2 continuation; N1 the knockout (fallback `causal_trace`), N2 `attention_temperature` → `attention_sensitivity`, N3 describe-the-media-first; U1 `logprob_entropy` → `self_consistency(n=10)`, U2 `format_sensitivity` (letter tasks); Sb describe-first, S1 `gradcam` → `generic_attention`, S2 `embed_lens`, S3 `patchscope` → `tuned_lens` → `layer_contrast`; X1 media removed instead of swapped. A layer is done once a candidate (or the battery step serving it) gave a valid observation on the route's FAIL cases, and exhausted once every candidate is gated off, failed or refused; a failure moves to the next fallback of the same layer, a valid result to the next layer. Each round every route with at least 3 FAIL cases proposes one candidate — H first, then by FAIL count — which runs on the route's FAIL cases and as many gold-matched PASS cases; candidates the model cannot run are passed over at no cost, so an API run goes straight to the behavioural ones. A layer done on a smaller sample is extended to the route's new cases first. The run stops when no route has a candidate, after `--triage-max-actions` decisions (default 12), or on the budget. Follow-up readings are means per route FAIL cohort and PASS controls, with the number of cases behind each: descriptive, no test, no mechanism named. Describe-first asks for 256 output tokens per call (POPE's own cap is 16); a backend that drops per-call settings is gated on the host's cap instead. Its readings include whether the model actually wrote a description first (`complied_*`, at least 5 more words than the plain re-ask), and the report warns when most cases did not: an unchanged answer from a model that never described does not test the question.

**Scored scheduler.** `--triage-scheduler scored` (report `triage_report.scored.{json,md}` next to the rules' report, sharing the ledger) makes one decision at a time: every feasible candidate — the next chunk of each active route's open or unfinished layer, the alternatives of its answered layers, the expansion, and the deferred battery steps not yet run on the current sample — gets `U = q·[D + T + C − R]₊ / (c + ε)` (`evalrx/eval_agent/probing/scoring.py`) and the highest wins, ties going to the soft order. D (prediction disagreement) is 0 until competing explanations with predictions exist; T is 1 for completing a step measured on part of a route (spread over its chunks by the share of the remaining FAIL cases each covers, as are D and R) or resolving a contradiction, and 0.5 for an expansion that may close a recorded gap; C is the coverage gap over layer × gold-stratum units the action removes; R filters observations that already exist (R = 1), and prices an answered layer's other candidates, its *alternatives*: 0.5 when one gives the kind of evidence the tool that answered the layer gave (`PlanStep.evidence`: a second attention rescaling, relevance map or layer readout), 0 when it gives another kind (a different intervention, e.g. `causal_trace` after the knockout). An alternative closes no gap and covers no unit, so it runs only on a D above its R; q is the analyzer's smoothed success rate in this run; c is the step's own measured cost on the primary axis (USD when every action is priced, else seconds), or the run's median cost per case for a step that has not run yet; one chunk of it shows the real cost before the next decision. Further chunks of a step already taken do not count against `--triage-max-actions`. Exploration has a share of the evidence spending, `--triage-explore-share` (default 0.1; the judge's calls are not counted), not of the decisions, and draws from its own targets — actions the value never takes: the next candidate of a route with too few FAIL cases to be active, and on each active route the representative of every other route's layer it does not own, when that step has readings to compare with the controls. Whenever a target fits — exploration's spending plus its conservative estimate (a budget check's) within the share — a seeded draw among them runs instead of the best candidate. Completing a target on its route is exploration too, paid from the share, until the cases measured so far show a reading outside its band (the verdicts' 95% interval): the step has then found something, and its completion is an incomplete step that T values like any other. The run stops once no candidate's gain reaches 0.01 and no target fits. `--triage-explore-from candidates` (an ablation) draws from the candidates other than the best instead, alternatives included. `--triage-weights` (e.g. `c=0`) sets the weights of D, T, C and R for ablations. While an expansion can still follow, batch-dependent candidates wait (any expansion would supersede them). With D = 0 the value of a candidate does not depend on what earlier actions found, so the scored scheduler only reorders: on Qwen3.5-0.8B POPE it reaches the rules' follow-ups and readings exactly, with twice the decisions. Decisions read only the scheduler's own evidence and price candidates as if they ran fresh, so a shared ledger saves compute without changing choices. Each decision lists every candidate's components; both schedulers' reports carry the evidence cost at first execution, the controller's own time and the coverage units, which `evalrx/eval_agent/probing/compare.py` puts side by side. `--triage-budget-usd` caps API spend like `--triage-budget-sec` caps seconds.

**Competing explanations (D).** With `--triage-scheduler scored --triage-explanations judge`, the chain's judge (`--judge-provider` / `--judge-model`, built without the coder checks since triage runs no coding stage; it must not be the model under test) proposes, per active route, up to three competing local explanations of why the route's FAIL cases fail, each predicting `up` / `down` / `same` / `unknown` for the readings of every tool still to run there: the direction of FAIL mean − PASS control mean against a band fixed per reading (`CARDS` in `evalrx/eval_agent/probing/explanations.py`; the judge picks directions, never the reading, comparison or threshold). It is asked once the sample has settled (an expansion revises the routes), and again, at most three asks in all, when the evidence has decided a prediction and a route with tools left has fewer than two live explanations; each ask sees the previous verdicts. Code checks every prediction: a hit when the 95% interval of the difference lies inside the predicted region, a miss outside it, else undetermined; an explanation with a miss is contradicted and leaves the live set at the next decision. A candidate's D sums, over the pairs of its route's live explanations whose predictions for it conflict, how decidable the conflict is on the route's cases, and divides by the number of pairs (a pair with `unknown` counts only in the denominator). Decidability takes each prediction in turn as true at a reference difference (0 for `same`, one standard deviation of the reading beyond the band for `up`/`down`) and asks how many cases a side the verdict's interval needs to contradict the other: each side scores `min(1, n / needed)` with the route's n FAIL cases, and the conflict the mean of the two sides. The spread comes from every case the step measured in this run; before that a share's spread is taken at its largest and a mean's band as negligible next to its spread, so an unmeasured "same" can never be contradicted and an up-versus-same conflict counts at most half. Three FAIL cases settle an unmeasured up-versus-same conflict to 1/6, sixteen to 1/2. The judge sees route summaries and readings of EXPLORE, never a case's content, media or CONFIRM; prompts, replies and costs are stored under `explanations/<key>.json`, so a resumed run reads replies back. A CLI judge reports no tokens, so its calls are charged in seconds; the judge's availability probe at start-up is not counted. A call is charged like an action: the judge is asked only while the largest call so far still fits the budget, so a run overshoots by at most its first call, whose cost nobody knows yet. The report is `triage_report.scored_d.{json,md}`, with each explanation's predictions and verdicts on the final evidence and whether the judge had already seen part of a reading when it predicted (such a hit is not out of sample); `compare.py` applies the explaining run's last explanations to both runs' final readings and counts the pairs each run's evidence tells apart. Each open layer's current candidate is offered for prediction, and every layer's other candidates as alternatives (`alternative_to`: the tool that answered the layer, or its current candidate), so their predictions exist once the layer is answered. On Qwen3.5-0.8B POPE decidability cuts D on the three-case N route from 0.67-1.0 to 0.11-0.22; of the 19 alternatives five D arms ran, 7 were chosen on value (mostly `self_consistency_n10` after `logprob_entropy`, another kind of evidence) and 12 by exploration, and the judge's three asks (about 130 s each) cost about 30% of the evidence time.

**Diagnostic validation (MVP-4).** The data roles are fixed before the controller sees a case and written to `<run>/partition_bundle.json`: DISCOVERY is EXPLORE; DIAGNOSTIC_VALIDATION is the CONFIRM partition minus every case whose media content also appears in DISCOVERY (on POPE, where each image carries a yes and a no question, the other question about a seen image is not a new image); `--confirm-split-by media` instead draws the explore/confirm split over media groups, whole images on one side, so nothing is left out (default `case`: the judge-driven loop's split, which a triage run must share to be compared case for case); repair CONFIRM is not part of this protocol. `--triage-validation-source MANIFEST` adds a validation-only source: cases the controller and the judge never see, labelled by their own Stage 0 pass (`<run>/baseline_validation_source.json`) and joining DIAGNOSTIC_VALIDATION under the same media rule, the bundle recording where its cases came from (ChartQA: `python -m evalrx.benchmark.tasks.chartqa <dir> --exclude <pool>/manifest.json` freezes the human-authored rows the discovery pool left, the rest of the test split and the val split). With `--triage-validate` the issues the triage report supports on DISCOVERY are frozen (`evalrx/eval_agent/probing/validation.py`): a route signal (a label-free H/N/U check firing more on FAIL than on matched PASS by more than 0.1, its whole 95% interval above that), or a reading difference on a route's FAIL cases against its matched controls beyond the reading's band (one issue per route and step, the reading furthest outside its band; a step re-measuring the check its route is cut on, or reading what it implies (the output's close calls on U), is left out). The family, a power plan from DISCOVERY only (the validation cases each issue should have and those it needs at the discovery effect) and the partition are written to `<run>/validation/frozen.json` before any validation case is read; then the route checks run on all validation FAIL cases and their matched PASS controls, each reading issue's step runs on its route, and every issue is judged on its interval at `1 - 2·0.05/K`, a one-sided test at 0.05/K on the side its direction claims (Bonferroni over the K issues): `supported`, `refuted`, `inconclusive` or `unavailable`. Several readings can say one thing, so two reading issues of a route whose per-case values go together on the validation cases, within the FAIL cases and within the controls (pooled within-group Spearman |rho| >= 0.5; a FAIL-vs-control shift alone does not count), are one phenomenon; each arm is credited with its own issues grouped that way. Where a correlation lies near the threshold the count depends on it, so the main metric is the number of supported phenomena over a grid of thresholds (0.3 to 0.7 in steps of 0.05), and an arm found more than another only where it has more at every threshold of the grid. No card reading reads the label: steps with a target read the model's own answer (`target="prediction"`), since a gold margin lower on FAIL cases restates that they are wrong, and a carded step targeting gold is refused. The validator uses the DISCOVERY-fixed artefacts (lens references, the tuned lens's fit set), draws swap donors from the validation cases, and writes its own ledger and `validation_report.{json,md}`; the judge's explanations live at the stop are frozen with the family (a re-ask keeps the live ones and adds competing new ones, so none is lost to a later ask); each names one or two primary predictions (the readings it stands or falls on; competing explanations must differ on one), on tools still to run on the route or already run there (with their readings in view: a fit during the triage, tested on new cases, no D), only those keep it live during the triage and enter D, and the validator runs their steps on the route's validation cases, tests the distinct primary predictions as one one-sided Bonferroni family and calls each explanation `supported`, `refuted`, `undecided` or `untestable` (other predictions reported at 95%; reported apart, not counted); a prediction on a reading the route is cut on or that it implies (re-sampling or the output's close calls on U) is never asked of the judge, and a route with only such steps left does not trigger a re-ask, and one met in an older report is labelled `definitional`, neither support nor contradiction. `--triage-validation-budget-sec` caps the validation's evidence.

The swap uses counterfactual donors drawn from the whole EXPLORE partition: a case asking the identical prompt about different media whose gold differs from the model's own answer, so a correct answer has to change (relative to the model's answer, not the case's gold, because on a failed case the two differ). On yes/no and letter tasks only such swaps test N; cases without one are reported as untested, so a larger `--limit` raises coverage (on POPE adversarial the questions repeat per object across images). Open-answer tasks also accept content-only swaps, recorded with that assumption.

U (an answer that moves) needs both of its parts: re-sampling at temperature 1.0 (with the run's `--top-p`/`--top-k` on local backends; temperature only on `--backend gemini`, whose runtime merges per-call settings; the `endpoint` backend drops per-call settings, so this part stays untested there), compared with the Stage-0 answer, and the two wrappers, compared with the question re-asked unchanged. Answers are compared by the task's answer key under its agreement rule (two numbers within the task's numeric tolerance of each other are one answer, as the grader holds them; re-sampled answers are clustered by it), not graded against the gold; an unreadable answer is set aside, and a wrapper with no readable answer is an invalid control. Re-sampling fires U when another answer was sampled more often than the Stage-0 answer (a tie does not; one differing sample is ordinary noise at temperature 1.0, most of all on open answers); a wrapper fires it when its readable answer differs. S is a FAIL case on which H, N (when the case has media) and both U parts ran and none fired; a missing check leaves the case in X, never in S. The threshold instruction, `embed_lens` and `patchscope` are attached to every case as descriptive S readings — whether the instruction fixes errors and what it breaks, how close the case's own question word gets to the media tokens, whether the model's own answer ranked first at some layer before the last, and whether the question word is decoded off the media tokens — and summarised for S failures, other failures and stable PASS controls by gold answer. They are not tests and name no mechanism.

On an API model (`--backend gemini`) the same plan runs with the white-box steps recorded as `unsupported` (nothing spent). Each action's cost carries what the provider counted — requests, retries, prompt/completion/thought tokens — and its USD at the dated listed price in `evalrx/models/backends/api/prices.py` (unknown for an unlisted model); Stage 0's usage goes into `baseline.json`. The rule-chosen follow-ups are gated on the actual model in the same way, so a run without internal state runs its behavioural follow-ups and records why the internal ones cannot run.

```bash
GEMINI_API_KEY=... python -m evalrx.benchmark.run --modality vlm --model gemini-3.1-flash-lite \
  --dataset pope_adversarial --limit 1000 --concurrency 8 \
  --m1-policy triage_active --triage-n-fail 32 --run-tag triage-api1
```

White-box edits refuse when their edit-free self-check fails, and the check runs on every analysed case: the first failing case refuses the whole batch. On Qwen3.5-0.8B in bf16, the attention tap reproduces `--attn-impl eager` exactly but differs from `sdpa` by 0.8–2.0% of the largest logit depending on the input, around the 1% tolerance, so `attention_knockout` (and the other tap-based analyzers) report `unfaithful` under `sdpa`; use `--attn-impl eager` for edit-based analyzers. This applies to the default `judge` path as well. Action identities include a hash of the analyzer's code, so a rerun after a code change re-executes the action. White-box margins compare the target answer with the strongest token that is not one of its spellings (`"Yes"` and `" Yes"` are different BPE ids that a model can split one answer across), so margins from runs before that change are not comparable.

## Failure and progress semantics

M3 exceptions are recorded as structured error exchanges with exception type, message, attempt, and retry status. The runtime automatically permits one additional attempt; valid empty diagnoses are not retried as transport failures. Exhaustion produces `diagnosis_error`, an error diagnosis status, and benchmark exit code 2 rather than a successful `no_hypotheses` result.

Repair progress prints proposal starts, candidate starts/completions, and case counters for ordinary template/spec evaluation, even while detailed result logging is deferred. These operational events contain no case IDs, labels, outputs, or correctness scores. Coded pipelines emit candidate start/end events; their internal calls are not represented as ordinary per-case counters.

## Scoring correction

The multiple-choice parser now recognizes balanced Markdown around a single option (for example `The correct answer is **A**.`). It preserves rejection of uncommitted thought-channel output and ambiguous option lists. This changes labels for affected historical outputs; keep old runs intact and rescore/rerun under the corrected scorer as a new result version. A parser fix alone is not evidence that the model or repair improved.
